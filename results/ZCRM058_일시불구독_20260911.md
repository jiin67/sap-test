### 결함: RFC 가 받은 CSLTNO 가 3자리 밀려 있음 (Critical)
- ET_RETURN 의 CSLTNO = 입력 문자열(CSLTNO 13자리 + CFDATE1 8자리)의 **4~16번째 문자**. 모든 케이스에서 동일한 규칙.
- SE37 입력 화면(Structure Editor)의 IT_DATA 행은 CSLTNO / CFDATE1 두 필드뿐이고 MANDT 가 없다 → 입력은 인터페이스대로 들어갔다.
- `{CSLTNO, CFDATE1}` 행을 MOVE-CORRESPONDING 이 아닌 단순 MOVE 로 `ZCRM_CHRG_CNFRM` 형(MANDT 3 + CSLTNO 13 + …) 작업영역에 옮기면 정확히 이 결과가 나온다 (MANDT 가 앞 3자리를 가져감). 소스 확인은 개발자 요청 필요 (GUI 스크립팅으로 소스 열람 불가).
- 영향: 유효한 상담번호가 전부 "존재하지 않는 상담번호" 로 거부 → 등록/취소가 한 건도 반영되지 않음. ZCRM_CHRG_CNFRM 은 여전히 0건 (SE16N 확인).

## RFC 결함 원인 확정 (소스 검토, 2026-09-12)

원인은 구조가 다른 변수에 통째로 대입한 두 곳이다. 둘 다 IT_DATA(라인타입 {CSLTNO(13), CFDATE1(8)})를
ZCRM_CHRG_CNFRM 형(MANDT(3) + CSLTNO(13) + SPMON(6) + CFDATE1(8) ...)에 바이트 단위로 옮긴다.

1. `DATA: ls_data TYPE ZCRM_CHRG_CNFRM.` + `LOOP AT it_data INTO ls_data.`
2. `DATA: lt_key TYPE STANDARD TABLE OF zcrm_chrg_cnfrm.` + `lt_key[] = it_data[].`

검증: 입력 "2026070100278" + "20260805" = 21자 → MANDT="202", CSLTNO=4~16번째="6070100278202".
실측값과 정확히 일치한다(확정일 공백이면 "…00000000" 이라 "6070100450000"). 2번 때문에 FOR ALL ENTRIES
SELECT 가 밀린 상담번호로 조회돼 lt_svc 가 비고, 1번 때문에 READ TABLE 키도 밀린다 → 전건 '존재하지 않는 상담번호'.

수정안: `ls_data TYPE LINE OF zcrmy074`, `lt_key TYPE zcrmy074` (라인타입을 인터페이스와 맞춘다).

부수 문제(같이 검토 권장): 취소(C) 시 미존재 행이면 DELETE FROM TABLE sy-subrc=4 → 전체 롤백 'A' 로 빠져
부분성공 원칙과 충돌 / 중복 제거 기준 aezet 는 한 호출 내 동일값이라 "마지막 전송값 우선" 보장 안 됨 /
MODIFY 가 ERNAM·ERDAT(생성이력)을 매번 덮어씀 / 검증 직후 'S' 를 APPEND 해 롤백 시 ET_RETURN 과 불일치.
